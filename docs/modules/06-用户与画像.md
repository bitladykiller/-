## 2.5 鉴权服务（v3.35 新增）⭐

文件：[`app/user/application/auth_service.py`](../../app/user/application/auth_service.py)
（API 端点见 [02-API接口.md](02-API接口.md) §4；时序图见 [00-全流程图集.md](00-全流程图集.md) §22）

### 2.5.1 为什么鉴权放在 user 域

身份是用户域的核心资产：`users.password_hash` 列从 init.sql 第一天就存在，
但 v3.35 之前从未被使用——API 让客户端自报 user_id。鉴权服务把这列
"激活"，user 域从"画像存储"升级为"身份权威"。

### 2.5.2 组成部件（教学拆解）

| 部件 | 实现 | 一句话原理 |
|---|---|---|
| 口令哈希 | `passlib` bcrypt | 单向 + 自动盐 + 可调成本因子：库泄露也无法还原明文；同一密码每次哈希结果不同（盐），`verify` 内部提取盐比对 |
| 令牌 | `PyJWT` HS256 | `header.payload.signature`，签名 = HMAC(SECRET_KEY)。服务端**无状态验证**：不查库、不存 session |
| 载荷 | `{sub: user_id, username, iat, exp}` | `sub` 是身份唯一来源；`exp` 由 `ACCESS_TOKEN_TTL_SECONDS` 控制 |
| 身份对象 | `AuthenticatedUser(id, username)`（frozen dataclass） | 验证通过后贯穿业务层的不可变凭证 |

### 2.5.3 三个安全设计决策（面试高频）

1. **登录失败统一文案**「用户名或密码错误」——区分"用户不存在/密码错"
   会泄露注册状态，给撞库者免费的探测接口。
2. **注册校验在纯函数** `validate_registration`（用户名 2–50、密码 ≥6）——
   规则可单测，不掺 IO。
3. **邮箱占位** `{username}@local.invalid`——schema 要求 email NOT NULL UNIQUE，
   未开放邮箱注册前用保留域名占位（`.invalid` 是 RFC 2606 保留 TLD，
   永不可达，不会误发邮件）。

### 2.5.4 与横切层的连接

`get_current_user`（api/deps.py）验证令牌后执行
`set_current_user_id(user.id)`——写入 contextvars。下游两个消费者：

- **日志**：无需业务代码传参（request_id 同机制）
- **RAG 分域**：`rag_visibility` 开启时，检索过滤
  `owner_id in ("global", 当前用户)` 直接从 contextvars 取身份

### 2.5.5 错误类型与映射

| 异常（服务层） | API 映射 | 场景 |
|---|---|---|
| `AuthError` | 401 | 凭据错 / 令牌过期 / 签名伪造 |
| `RegistrationError` | 400 | 用户名占用 / 参数不合规 |
| `ResourceNotFoundError` | 404 | `get_user` 查无此人 |

### 2.5.6 相关测试

`tests/user/test_auth_service.py`（哈希回环 / 过期拒绝 / 篡改拒绝 /
**他人密钥签发的伪造令牌拒绝** / 注册规则）、`tests/api/test_auth_api.py`
（401 语义 / contextvars 写入 / 端点错误映射）。

## 5. Repository（MySQL）与版本化更新流

```mermaid
sequenceDiagram
    autonumber
    participant Memory as MemoryMiddleware / Extractor
    participant Adapter as ProfileAdapter
    participant Service as UserProfileService
    participant Redis as Redis Cache
    participant Repo as UserProfileRepository
    participant MySQL as MySQL (user_profiles & user_facts)

    rect rgb(240, 255, 240)
        note over Memory, MySQL: 画像读取流 (Cache-Aside 策略)
        Memory->>Adapter: load_user_profile(user_id)
        Adapter->>Service: get_profile(user_id)
        Service->>Redis: GET user_profile:{user_id}
        alt 缓存命中
            Redis-->>Service: 返回 JSON 画像数据
        else 缓存未命中
            Service->>Repo: get_profile_data(user_id)
            Repo->>MySQL: SELECT * FROM user_profiles JOIN active user_facts
            MySQL-->>Repo: 返回数据库记录
            Repo-->>Service: 构造成 UserProfileData
            Service->>Redis: SETEX user_profile:{user_id} 86400s
        end
        Service-->>Adapter: 返回 UserProfilePayload
    end

    rect rgb(255, 245, 230)
        note over Memory, MySQL: 画像与 Facts 版本化更新流
        Memory->>Adapter: save_user_profile(user_id, extracted_candidate)
        Adapter->>Service: upsert_profile_data(user_id, candidate)
        Service->>Repo: upsert_profile_data(...)
        
        opt 新增/更替 Fact 事实
            Repo->>MySQL: UPDATE user_facts SET is_active=false, superseded_at=NOW() WHERE key = target_key
            Repo->>MySQL: INSERT INTO user_facts (user_id, key, value, version, is_active=true)
        end
        
        Repo->>MySQL: UPSERT INTO user_profiles
        Repo-->>Service: 更新成功
        Service->>Redis: DELETE user_profile:{user_id} (主动作废缓存)
    end
```

## 6. Service（缓存编排）

文件：`app/user/application/user_profile_service.py`  
单例：`user_profile_service`

### 6.1 缓存约定

| 项 | 值 |
|---|---|
| Key | `user:profile:{user_id}` |
| TTL | `settings.app_config.memory.user_profile_cache_ttl`（默认约 1800s） |
| 客户端 | 由调用方传入 Redis（MemoryMiddleware 传入 STM 的 redis） |

### 6.2 `get_profile`（函数级）

```python
async def get_profile(
    self,
    user_id: int,
    redis_client: ProfileCache | None = None,
) -> UserProfilePayload
```

```text
1. Redis GET key=user:profile:{user_id} → JSON → coerce/normalize
2. 未命中 → repository.get_profile(db, user_id)
3. 回填 Redis SETEX(ttl=user_profile_cache_ttl)
4. 任意失败 → empty_profile(user_id)（warning 日志，不抛给主对话）
```

### 6.3 `upsert_profile_data`（函数级）

```python
async def upsert_profile_data(
    self,
    user_id: int,
    profile: UserProfileData,
    redis_client: ProfileCache | None = None,
) -> bool
```

```text
1. profile 空 → True（noop）
2. repository.upsert_profile_data + commit（主字段 + facts 版本化）
3. 有变更则 DELETE 缓存 key（下次 get 重建）
4. 失败 → False + warning
```

**Repository 侧常见方法：** `get_profile` / `upsert_profile_fields` / `upsert_fact`（facts 版本链，见面试深挖）。

## 面试深挖：用户与画像

### Q1. facts 为何版本化而不是 UPDATE 覆盖？

`upsert_fact`：值相同 return False；不同则 deactivate 旧行、insert version+1、superseded_by 链接。  
可追溯「用户预算从 3k 变成 5k」的历史，便于审计与回滚分析。

### Q2. 缓存一致性？

读：Redis → MySQL → 回填。  
写：DB commit 成功且 data_changed → **DELETE** cache（不是写穿更新），下次读重建。简单可靠。

### Q3. 空画像为何还返回结构？

`empty_profile` 保证 Prompt/类型稳定，避免 None 分叉；字段全 None/[]。

### Q4. knowledge 如何更新画像还不反向依赖？

`profile_adapter` 在 knowledge 包内，**import user.application**；user 永不 import knowledge。单向依赖。

### Q5. 为什么删会话不删画像？

因为画像是用户级 durable 资产，不是单会话的临时上下文。  
删会话时应该清掉 STM 和按 `session_id` 绑定的 LTM，但不应该把用户长期偏好和事实历史一起抹掉。

## 11. 当前边界与生产化改进

### 11.1 当前边界

1. 当前没有登录鉴权，`user_id` 来自调用方，默认信任外部传入。
2. 当前没有对外的“删除用户并清理全部画像/记忆”的完整 API。
3. 画像缓存是 **删除缓存、下次重建**，不是写穿更新；这是保守做法，但不是最低延迟做法。
4. `user_facts` 做了版本化，但当前主要强调可追溯，没有额外做历史版本归档和保留策略管理。
5. 删除会话时不会删除用户画像，因为画像是跨会话 durable 资产，不归单会话所有。

### 11.2 为什么这些边界值得主动讲

因为这能体现你对系统边界是清楚的，而不是只会背“这里用了 Redis 缓存、那里用了 MySQL 表”。

面试时可以这样表达：

```text
当前实现重点是把画像和对话记忆拆开：画像是用户级 durable 资产，记忆是会话级增强上下文。
所以删会话会清 STM/LTM，但不会清画像；如果未来要做用户注销，需要单独补用户级数据治理链路。
```

## 12. 实习面试讲法

### 12.1 这一块最值得讲什么

1. 画像为什么不放进 knowledge 域，而是放进 user 域。
2. 为什么 `user_facts` 要版本化，而不是直接更新。
3. 为什么缓存更新采用“DB commit 成功后删缓存，下次重建”。
4. 为什么删会话不删画像。

### 12.2 60 秒讲法模板

```text
用户画像这块我理解成两层：一层是 user_profiles 这种相对稳定的主字段，比如偏好品牌、预算范围、偏好品类；另一层是 user_facts 这种可变事实，比如用户最近提到过的需求或偏好，它做了 version 化而不是直接覆盖。读取时先走 Redis 缓存，miss 了再查 MySQL，写入时数据库提交成功后删缓存。知识域不会直接拥有画像表，而是通过 profile_adapter 调 user 域服务，这样 durable 用户数据和对话记忆的边界就比较清楚。
```

### 12.3 如果被追问“你觉得这里还有什么可以改”

1. 增加 JWT 和 user_id 真实性校验。
2. 增加删除用户时的画像、缓存、记忆一体化清理流程。
3. 给 facts 增加更细粒度的来源、置信度和更新时间策略。
4. 如果画像字段继续变多，可以从 TypedDict 逐步升级到更强约束的数据模型和迁移方案。

## U3. Service 缓存时序（必画）

```text
get_profile(user_id, redis?):
  key = user:profile:{user_id}
  if redis:
    GET → json.loads → coerce_user_profile_payload
  else miss:
    MySQL get_profile
    SETEX key TTL profile_json
  on error → empty_profile（主对话不崩）

upsert_profile_data(user_id, profile, redis?):
  if profile empty → True
  MySQL upsert + commit
  if changed and redis: DELETE key   # 下次 get 重建
  on error → False
```

TTL：`settings.app_config.memory.user_profile_cache_ttl`（默认 1800s）。

## 附录 U · 函数手册：用户域逐函数明细

> 签名与源码逐字一致（v3.35.1）。📌=热路径 ⚠️=历史踩坑。

### U.1 `application/auth_service.py`

#### 纯函数（哈希与令牌）

| 函数 | 签名 | 要点 |
|---|---|---|
| `hash_password` | `(plain: str) -> str` | passlib bcrypt：自动盐+成本因子；同一密码每次结果不同 |
| `verify_password` | `(plain, hashed) -> bool` | verify 内部提取盐比对；**畸形哈希按验证失败**（不向上暴露库异常） |
| `issue_access_token` | `(user_id, username, *, now=None, ttl_seconds=None) -> str` | JWT HS256(SECRET_KEY)；payload `{sub:str(id), username, iat, exp}`；now/ttl 可注入（测过期用例免 sleep） |
| `verify_access_token` | `(token) -> AuthenticatedUser` | ExpiredSignatureError→AuthError「登录已过期」；InvalidTokenError→「无效的访问令牌」；载荷 sub 非数字/缺 username→「令牌载荷缺失」 |
| `validate_registration` | `(username, password) -> None` | 用户名 2–50、密码 ≥6；违规 RegistrationError（纯函数可单测，不掺 IO） |

#### 异常与身份对象

- `AuthError(message="用户名或密码错误")`→API 401；
  `RegistrationError(message)`→API 400；
- `@dataclass(frozen=True) AuthenticatedUser(id, username)`：验证后贯穿
  业务层的不可变凭证。

#### `class AuthService`

`__init__(session_factory=None)`：缺省 AsyncSessionLocal，可注入测试工厂。

| 方法 | 流程 | 失败语义 |
|---|---|---|
| `register(username, password) -> AuthenticatedUser` | 校验→查重名→bcrypt→插行（email 占位 `{name}@local.invalid`：schema NOT NULL UNIQUE，`.invalid` 是 RFC 2606 保留 TLD 永不可达）→commit+refresh | 占用/不合规 RegistrationError |
| 📌 `authenticate(username, password)` | 查行→verify_password→刷 last_login→commit | **统一 AuthError**（不区分不存在/密码错，防撞库探测注册状态） |
| `get_user(user_id)` | 按 id 查 | 无→ResourceNotFoundError |

模块单例 `auth_service`；API 层（auth.py/deps.py）唯一消费方。

### U.2 `domain/profile_payload_support.py` — 画像数据收口纯函数

外部输入（LLM 抽取/缓存 JSON）都是松散 dict，这组函数把它们**收口**成
稳定结构——脏数据在边界处理，内层逻辑零判空。

| 函数 | 签名 | 收口规则 |
|---|---|---|
| `normalize_optional_text` | `(value) -> str \| None` | 非 str/空白→None；否则 strip |
| `normalize_profile_tags` | `(raw_tags) -> list[str]` | 滤空/非 str/重复，**保持原始顺序**（有序去重） |
| `normalize_profile_facts` | `(raw_facts) -> list[UserProfileFact]` | 仅收 {key,value} 均为非空 str 的条目 |
| `normalize_profile_data` | `(raw_profile) -> UserProfileData` | 三主字段+tags+facts 全走上述规则；非 dict→空结构 |
| `coerce_user_profile_payload` | `(user_id, raw_profile) -> UserProfilePayload` | normalize + 注入 user_id（缓存反序列化入口） |

### U.3 `application/user_profile_service.py`

`ProfileCache` Protocol：`get(key) -> str|bytes|None` / `setex` / `delete`
——⚠️ 返回类型含 bytes：STM 共用的 Redis 客户端是二进制安全的
（decode_responses=False），`json.loads` 原生接受 bytes。

#### `class UserProfileService`（Cache-Aside 模式）

| 方法 | 流程 | 要点 |
|---|---|---|
| 📌 `get_profile(user_id, redis_client=None) -> UserProfilePayload` | 缓存命中→coerce 返回（坏 JSON 静默落库路径）；未命中→MySQL→回填 setex(TTL 1800)→返回 | 读全程异常→warning+**empty_profile**（画像是增强项） |
| `upsert_profile_data(user_id, profile, redis_client=None) -> bool` | 空 profile 直接 True；repo 事务 upsert→**data_changed 才 commit**→变更才 delete 缓存 | 写失败 False；**失效而非更新缓存**（下次读回源，避免双写不一致） |

### U.4 `infrastructure/repository/user_profile_repository.py`

#### 模块级纯函数

| 函数 | 要点 |
|---|---|
| `_decode_profile_tags_json(raw) -> list[str]` | 库里 tags 是 JSON 文本；坏值→[] |
| `_build_user_profile_facts(rows) -> list[UserProfileFact]` | 行→{key,value}，滤空 |
| `_build_profile_field_values(*, preferred_brand, budget_range, preferred_category, tags) -> dict[str,str]` | 只保留非空字段；tags 序列化 JSON——**upsert 只碰传入的字段** |

#### `class UserProfileRepository`

| 方法 | 签名 | 要点 |
|---|---|---|
| `empty_profile(user_id)` | staticmethod | 默认空结构（读失败兜底/新用户） |
| `get_profile(db, user_id) -> UserProfilePayload` | | 画像行 + 激活 facts 两查合一 payload |
| `upsert_profile_fields(db, *, user_id, …) -> bool` | | 无有效字段 False（**不发起空写**）；存在则 UPDATE 否则 INSERT |
| `upsert_fact(db, *, user_id, fact_key, fact_value) -> bool` | | **版本化**：同 key 值变 → 旧行 is_active=0 + 插新行（事实演变可追溯）；值相同 → False 不写 |
| `upsert_profile_data(db, *, user_id, profile) -> bool` | | 批量编排：字段 upsert + 逐条 fact upsert；返回"是否真的改了"（服务层据此决定 commit 与缓存失效） |

### U.5 `infrastructure/models/user.py`

`class User(Base)`：id / username(unique) / **email(unique)** /
**password_hash** / status(默认 active) / last_login / created_at +
conversations 关系（cascade delete-orphan）。
⚠️ v3.35 前 ORM 只映射 id+username——password_hash 在库里闲置多年。
`USER_STATUS_ACTIVE = "active"` 常量导出。
