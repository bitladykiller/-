## 0.1 学习导航

### 这一章的核心目标

你不是要把“记忆系统”当成一个抽象名词记住，而是要回答清楚：

1. 为什么这里不是简单地把历史消息全拼进 Prompt。
2. 为什么要有 P0、P1、P2、P3 四层。
3. 为什么记忆读写要挂在 `before_agent` / `after_agent`。

### 读这一章前最好先知道什么

1. 记忆系统并不只等于 Redis。
2. 画像、摘要、长期记忆虽然都和“记住用户”有关，但作用完全不同。
3. AI 应用里的记忆重点不只是“能记住”，还包括“记错了怎么办、依赖挂了怎么办”。

### 这一章学完后你应该会什么

1. 能解释 P0-P3 分层及其优先级。
2. 能讲清 `before_agent` 读什么、`after_agent` 写什么。
3. 能解释 STM 为什么要压缩，LTM 为什么要检索和去重。
4. 能讲清删除会话时为什么要连带清理 STM / LTM。

### 推荐阅读方法

1. 先看 §0 图和 §1 分层，建立整体视图。
2. 再看 §3 MemoryMiddleware 编排，把读写顺序吃透。
3. 再看 §4 STM、§5 LTM，区分短期和长期能力。
4. 最后看“面试深挖”和附录 B，转成面试问答。

### 常见误区

1. 把画像和长期记忆混成一个概念。
2. 只会说“Redis 存历史消息”，但讲不清为什么还需要摘要和压缩。
3. 认为记忆失败就等于主对话一定失败，没有意识到这里做了降级。

## 1. 目标与分层

| 层级 | 存储 | 时效 | 职责 |
|---|---|---|---|
| **P0 最近消息** | Redis STM ZSET 窗口 | TTL 默认 24h | 当前会话权威上下文 |
| **P1 用户画像** | MySQL + Redis cache | durable | 品牌/预算/品类/标签/facts |
| **P2 会话摘要** | Redis STM summary | 随会话 | 压缩后的旧轮次 |
| **P3 长期记忆** | Milvus LTM | durable + 衰减/命中 | issue_history / solution_note |

冲突时优先级：**P0 > P1 > P2 > P3**（注入文案写死在 `memory_context.py`）。

## 2.5 写扩散与读扩散 —— 记忆系统的核心设计范式 ⭐

> 这是理解整个记忆系统"为什么长这样"的钥匙。搞懂这一节，
> §3 的编排代码就只是这个范式的直译。

### 2.5.1 概念：一分钟版

这对概念来自 Feed 流系统设计（微博时间线是经典案例）：

| | 写扩散（fan-out on write） | 读扩散（fan-out on read） |
|---|---|---|
| 核心思想 | **写入时**就把数据加工成各消费方需要的形态（物化视图） | **读取时**才现场从多个来源拉取并组装 |
| 写成本 | 高（一次写 → N 份视图，写放大） | 低（只写一份原始数据） |
| 读成本 | 低（读现成的） | 高（读时 N 路查询 + 组装） |
| 数据新鲜度 | 视图可能滞后（异步物化） | 永远是最新的 |
| 适用 | 读远多于写、读延迟敏感 | 来源异构无法预 join、写远多于读 |

微博的取舍：给大 V 发帖做写扩散（推给千万粉丝收件箱）会写爆，
所以大 V 走读扩散、普通人走写扩散——**混合**才是常态。本系统同样是混合。

### 2.5.2 本系统的写扩散：一轮对话 → 五个物化视图

用户的一轮对话（user + assistant 两条消息）在 `turn_completed` 事件的
消费者里被**扩散写**到五个针对不同读场景优化的视图：

```mermaid
flowchart TB
    TURN["一轮对话完成<br/>(user_message, assistant_message)"]
    TURN -->|"after_response 发布"| EV[["turn_completed 事件<br/>Redis Streams / 崩溃可重放"]]
    EV --> C["消费者 handle_turn_completed"]

    C --> V1["视图① MySQL messages<br/>append-only 完整历史<br/><i>读场景：人看——切回旧会话、审计</i>"]
    C --> V2["视图② Redis STM 消息窗口<br/>ZSET 滑动窗口 + 压缩编码<br/><i>读场景：模型看——P0 最近上下文</i>"]
    V2 --> COND{"达到压缩阈值?<br/>(6 轮 或 20 条)"}
    COND -->|是| V3["视图③ Redis 会话摘要<br/>LLM 压缩旧消息<br/><i>读场景：P2 长对话的廉价上下文</i>"]
    V3 --> V4["视图④ Milvus LTM<br/>LLM 抽取语义记忆 + embedding<br/><i>读场景：P3 跨会话语义检索</i>"]
    V3 --> V5["视图⑤ MySQL 画像 + Redis 缓存<br/>LLM 提炼偏好/事实<br/><i>读场景：P1 稳定用户特征</i>"]
    COND -->|否| END[本轮到此为止]
```

三个刻意的设计决策：

1. **写扩散必须异步**。视图③④⑤各需要一次 LLM 调用（摘要/抽取/提炼），
   动辄数秒。答案已经通过 SSE 发出，用户不该为"系统内部记账"等待——
   所以 `after_response` 只发布事件就返回，扩散在消费者里展开。
2. **异步就必须可靠**。fire-and-forget 协程随进程共存亡；事件在
   Redis Streams 的 PEL 里，进程崩溃后被 `XAUTOCLAIM` 认领重放，
   失败有重试上限与死信流。**写扩散丢一环，对应优先级的记忆就永久缺失**
   （摘要丢了 P2 就空、抽取丢了 P3 就空），可靠性不是锦上添花。
3. **昂贵的视图按需物化**。①②每轮都写（便宜）；③④⑤只在压缩阈值
   触发时才做（LLM 成本高、且积累几轮后摘要/抽取的语义更完整）。
   这是写扩散的成本控制阀门——不是所有视图都值得每次写。

### 2.5.3 本系统的读扩散：一次提问 → 三路并发拉取

`before_agent` 在每轮问答开始时，从三套**异构存储**现场拉取并组装上下文：

```mermaid
flowchart LR
    Q[用户提问] --> BA[before_agent]
    BA -.->|asyncio.gather 并发| R1 & R2 & R3
    subgraph 读扩散["三路读扩散（互不依赖）"]
        R1["_read_short_term<br/>Redis: 摘要 + 最近消息<br/>(视图②③)"]
        R2["_read_user_profile<br/>MySQL+Redis缓存: 画像<br/>(视图⑤)"]
        R3["_read_long_term<br/>Milvus: embedding + 混合检索<br/>(视图④，最慢的一路)"]
    end
    R1 & R2 & R3 --> ASM["build_memory_context<br/>按 P0>P1>P2>P3 组装注入"]
    ASM --> LLM[进入主图推理]
```

为什么这里选读扩散而不是"再物化一层大宽表"？

- **无法预 join**：P3 长期记忆的召回依赖**当前问题**的语义
  （embedding 相似度），提问之前不存在"可以预先算好的结果"。
  这是读扩散的硬理由——查询参数是读时才知道的。
- **来源异构**：Redis ZSET、MySQL 行、Milvus 向量，三种数据模型
  硬拼成一份物化视图，维护成本远超三路并发读。
- **读扩散的代价用并发抵掉**：三路互不依赖，`asyncio.gather` 让总延迟
  = max(三路) 而不是 sum(三路)。这就是 v3.33 那轮性能优化的本质：
  **读扩散系统的第一优化永远是"把串行读改并发"**。

### 2.5.4 合起来看：一条数据的完整生命周期

```mermaid
sequenceDiagram
    autonumber
    participant U as 用户
    participant API as SSE 接口
    participant G as LangGraph
    participant EV as Redis Streams
    participant C as 事件消费者
    participant S as 五个视图存储

    Note over U,S: ── 第 N 轮：读扩散（同步，延迟敏感）──
    U->>API: 提问
    API->>G: astream
    G->>S: before_agent 三路并发读（现成视图）
    S-->>G: P0-P3 上下文
    G-->>U: SSE 流式答案（用户等待到此为止）

    Note over U,S: ── 第 N 轮：写扩散（异步，可靠性敏感）──
    G->>EV: publish turn_completed
    EV->>C: 消费（崩溃则 XAUTOCLAIM 重放）
    C->>S: 历史 → STM → (阈值) 摘要 → LTM → 画像
    Note over C,S: 第 N+1 轮的读扩散读到的就是这里物化的视图
```

**一句话总结**：写扩散把"贵"移到用户看不见的异步链路里换取读时便宜；
读扩散处理"读时才知道查询条件"的场景并用并发压延迟。
两者不是二选一，而是按每类数据的读写特征分别选择。

### 2.5.5 什么情况下这套取舍要重新评估

教学式文档不该只讲"现在为什么对"，还要讲"什么时候会变错"：

| 变化 | 受冲击的选择 | 演进方向 |
|---|---|---|
| 单用户 QPS 变高（如机器人刷问） | 写扩散的 LLM 成本被放大 | 压缩阈值调高 / 抽取采样化 |
| LTM 数据量暴涨、检索变慢 | 读扩散最慢一路拖高 max() | 给 P3 加超时预算，超时放弃该路（部分读扩散） |
| 需要"用户全景页"（一次看全部记忆） | 读扩散每次现拼太贵 | 为该页面**增加**一个写扩散视图（新消费者订阅同一事件） |
| 多租户隔离要求 | 两者都要加 tenant 过滤 | 事件与视图 key 已带 tenant_id，扩展点已留好 |

> 注意最后一行的模式：**新增读场景 = 给同一个事件流加一个新消费者**，
> 而不是改写现有链路。这是把写扩散建在事件管线上的最大红利。

### 面试深挖：写扩散/读扩散

**Q: 为什么消息要同时写 MySQL 和 Redis STM，不是冗余吗？**
A: 是刻意的双视图，读场景完全不同：MySQL messages 是给**人**看的
append-only 完整历史（永不参与推理）；STM 是给**模型**看的滑动窗口
（16 条上限 + 24h TTL + 压缩编码）。用一份数据同时服务两种读，
要么历史被窗口截断，要么模型上下文无限膨胀。

**Q: 写扩散链路里某一环失败会怎样？**
A: 分两层。环与环之间：历史落库失败不阻断记忆写入（互相独立降级）；
事件层面：整个 handler 抛出才触发 stream 重试，最多 3 次后进死信流
（可人工检查）。设计原则是"单环失败只缺对应视图，绝不放大成整轮丢失"。

**Q: 读扩散三路里有一路挂了怎么办？**
A: 每路独立 try/except 降级为空值（该优先级的记忆缺席），其余照常注入。
记忆是增强项——三路全挂，对话也必须能继续（裸 LLM 模式）。

```mermaid
            Extractor-->>MM: 返回 MemoryExtractorResult (LTM 记忆 + 画像 Candidate)
            opt 抽取到 LTM 记忆
                MM->>LTM: save_memory(issue_history/solution_note)
            end
            opt 抽取到新 Facts/偏好
                MM->>Profile: save_user_profile(updated_facts)
            end
        end
    end
```

依赖注入：

- `redis_stm: RedisShortTermMemory`  
- `milvus_ltm: SimpleLongTermMemory`  
- `memory_extractor: MemoryExtractor`  
- `profile_reader/writer` 默认 `profile_adapter.load/save_user_profile`  

### 3.1 `before_agent(tenant, user, session, user_input)`

三路读取落在三套互不相干的存储上、彼此无数据依赖，因此 **并发发起**
（`asyncio.gather`）——耗时从「三者之和」降为「三者最大值」。
这是每轮对话的必经路径，其中 LTM 还要跑 embedding + 向量检索，通常最慢。

```text
并发执行以下三路，任一路失败只降级该路：

  A. _read_short_term:  get_summary ‖ get_recent_messages
                        失败 → (None, [])
  B. _read_user_profile: user_id 可解析为 >0 才读 profile_reader(uid, redis)
                        匿名 → None（不覆盖默认画像）；失败 → {}
  C. _read_long_term:   ltm_enabled 才 milvus_ltm.hybrid_search(...)
                        未启用或失败 → []

汇总为 AgentMemoryState 返回
```

> 并发的副作用：三路降级告警的**到达顺序不确定**，断言时不要依赖顺序。

### 3.2 `after_agent(...)`

> **执行时机（v3.35.0 起）**：`after_response` 图节点**发布 `turn_completed`
> 事件**（Redis Streams），由消费者执行"MySQL 历史落库 + 本函数"；
> 进程崩溃后消息被 XAUTOCLAIM 认领自动重放，失败有重试上限与死信。
> 事件基础设施不可用时回退为进程内 fire-and-forget（v3.34.0 行为，
> `flush_pending_memory_writes()` 仍可等待在途写入）。
> 无论哪条路径，记忆写入都不在 SSE 关键路径上。

```text
1. 读取 SessionMeta，total_turns += 1
2. append_messages(user + assistant)   ← 一轮两条合并成一次 Redis 往返
3. save_meta + refresh_ttl
4. 复用第 1 步的 meta（不再重读一次），若 should_compress:
     compress_session_memory(summary_compressor=LLM)
     若压缩成功且 ltm_enabled:
       extractor.extract(user, assistant, new_summary)
       → 语义记忆 dedup + save_memory
       → profile 非空则 profile_writer
5. 可选：update_memory_hit_infos(全部命中)  ← 一次批量 upsert，不逐条往返
```

所有 Redis/Milvus 异常以**降级 + 单次告警**为主，避免刷屏和拖垮主对话。

**降级日志分级（v3.33.0 起）**——统一走 `app.shared.core.degradation.log_degradation`：

| 异常类别 | 判定 | 日志级别 | 是否带堆栈 |
|---|---|---|---|
| Redis 错误 / 超时 / 连接失败 / OSError | 可预期的外部依赖故障 | `warning` | 否 |
| 其余全部（TypeError、AttributeError…） | **疑似代码缺陷** | `error`（`logger.exception`） | **是** |

> WHY 要分级：此前两类共用一句无异常信息的 warning，代码缺陷和网络抖动在日志里
> 长得一模一样。项目真实踩过——LTM 配置是 frozen dataclass 却被按 dict 下标取值，
> 每次调用抛 `TypeError` 被吞掉，表现为「长期记忆静默失效」：不报错，
> 只是永远检索不到、也永远写不进去。

## 3.9 STM Redis 客户端：必须二进制安全

STM 消息经 `compress_message` 压缩为二进制 MsgPack/Zstd（首字节 `\x00`-`\x03`），
**不是合法 UTF-8**。因此 STM 客户端必须用
`create_stm_redis_client()`（`decode_responses=False`）构造。

> 踩坑记录（v3.34.0 修复）：曾用 `decode_responses=True` 的客户端——
> 写入正常，`zrevrange` 读取时 redis-py 严格 UTF-8 解码抛
> `UnicodeDecodeError`，被降级逻辑吞掉，表现为**短期记忆写得进、读不出，
> 每轮对话拿到的最近消息恒为空**。读路径（`decode_model`/`decode_messages`）
> 原生支持 bytes；画像缓存存 JSON 文本，`json.loads` 同样接受 bytes。

### 5.4 SimpleLongTermMemory 方法过程

| 方法 | 过程 |
|---|---|

## 14. MemoryExtractor 内部过程

文件：`orchestration/memory_extractor.py`

```text
extract(user_message, assistant_message, session_summary?)
  1. extract_summary_text(session_summary)  # SessionSummary→纯文本
  2. 组 prompt，调用 self.llm_client.ainvoke
  3. extract_response_text(response)  # 兼容 str / content list
  4. parse_llm_response → parse_first_json_object
  5. build_semantic_memories(parsed):
       - 只保留配置允许的 memory_type（issue_history / solution_note）
       - 过滤寒暄集合（你好/谢谢/…）
       - 过滤过短 content
       - 手机号脱敏 1xx****xxxx；身份证/银行卡/邮箱 pattern 处理
       - 敏感词 pattern 命中则丢弃
  6. profile = normalize_profile_data(parsed.get("profile"))
  7. 返回 (semantic_memories, profile)
```

调用点：仅在 `after_agent` **压缩成功且 ltm_enabled** 时触发（不是每轮都抽）。

## 15. STM 压缩触发与步骤（实现级）

```text
should_compress(total_turns, last_compressed_turn, msg_count):
  默认 compression.enabled
  且 (total_turns - last_compressed_turn >= trigger_rounds=6
      或 msg_count >= trigger_messages=20)

compress_session_memory(...):
  1. 加 lock key
  2. 取较旧消息（保留 keep_recent_rounds=4 对应的最近消息）
  3. summary_compressor(old_summary, old_messages) → LLM 文本
  4. 解析/保存 SessionSummary
  5. 裁剪 messages 窗口
  6. 更新 last_compressed_turn
  7. 释放 lock
```

消息编解码：`compress_message` / `decompress_message`（MsgPack，可选 Zstd）。

## 面试深挖：记忆系统

### Q1. P0>P1>P2>P3 的业务理由？

| 优先级 | 可信度逻辑 |
|---|---|
| P0 最近对话 | 用户刚说的，最新意图 |
| P1 画像 | 跨会话稳定偏好，但可能过时 |
| P2 摘要 | 压缩有损，可能丢细节 |
| P3 LTM | 历史语义，噪声/过期风险最高 |

冲突时以最近对话为准，避免「旧画像锁死新需求」。

### Q2. 消息压缩的字节格式？（非常容易被问）

`compress_message`：

| packed 长度 | 前缀 flag | 算法 |
|---|---|---|
| ≤2KB | `0x00` | 仅 MsgPack |
| ≤4KB | `0x01` | MsgPack + Zstd level 1 |
| ≤16KB | `0x02` | MsgPack + Zstd level 3 |
| >16KB | `0x03` | MsgPack + Zstd level 9 |

解压：flag∈{1,2,3} 走 ZstdDecompressor，否则纯 MsgPack。**解压端不需要知道 level**。

### Q3. 为何不是每轮都抽 LTM？

只在 **压缩成功且 ltm_enabled** 时 `extract`：  
- 控制 LLM 成本  
- 压缩点=信息沉淀点，语义更完整  
- 减少寒暄轮次污染长期库  

### Q4. 敏感信息怎么处理？

配置 `SENSITIVE_PATTERNS`：密码/验证码/身份证/银行卡/token/手机号。  
Extractor：手机号脱敏 `138****5678` 式；命中敏感则丢弃该条语义记忆。

### Q5. before_agent 部分失败会怎样？

Redis 挂 → 空 STM；画像挂 → {}；Milvus 挂 → []。  
**warn_once** 同类警告只打一次，防日志雪崩。主对话继续。

### Q6. session 维度是什么？

`tenant_id`（默认 default）+ `user_id` + `session_id(=thread_id)`。  
多租户预留 tenant；当前单租户即可。

### Q6.1 删除会话会清哪些记忆？

`DELETE /api/conversations/{id}` 成功后会联动：

| 存储 | 行为 |
|---|---|
| MySQL | 删会话元信息；兼容清理历史 `messages` 行 |
| Redis STM | `clear_session` 删除 messages/summary/meta/lock |
| Milvus LTM | 按 `session_id` 软删除（`is_deleted=true`） |

注意：

- LTM 写入时会带上当前 `session_id`（`after_agent` → `save_memory`）
- 历史无 `session_id` 的 LTM 不会被会话删除命中，避免误删跨会话记忆
- 记忆清理失败不回滚 MySQL 删除（只打日志）

### Q7. LTM 去重阈值 0.88 vs 检索 0.72？

- 检索 0.72：召回可稍松  
- 去重 0.88：更严，避免近重复写入  
面试可说「写路径比读路径更保守」。

## 15.5 关键函数（编排与清理）

### `MemoryMiddleware.before_agent`

```python
async def before_agent(
    self,
    tenant_id: str,
    user_id: str,
    session_id: str,
    user_input: str,
) -> AgentMemoryState
```

三路并发（`asyncio.gather`），任一路失败只降级该路：

| 读取 | 失败降级 |
|---|---|
| `_read_short_term`：`get_summary` ‖ `get_recent_messages` | summary=None，messages=[] |
| `_read_user_profile`：`profile_reader(uid)`（uid 可转 int） | `{}`（匿名返回 None） |
| `_read_long_term`：`milvus_ltm.hybrid_search(...)`（ltm_enabled） | `[]` |

同类错误用 `_degrade_once` 按 key 去重，避免刷屏；首次记录会经
`log_degradation` 分级——外部故障 warning，非预期异常 error + 完整堆栈。

### `MemoryMiddleware.after_agent`（职责摘要）

写入本轮 user/assistant（`append_messages` 单次往返）→ `should_compress` 则压缩 → 抽取 LTM / 更新画像 → 可选 `update_memory_hit_infos`（批量刷新命中）。  
实现细节见上文 §3 / §14–15。

### STM / LTM 清理（删会话用）

```python
# RedisShortTermMemory
async def clear_session(tenant_id, user_id, session_id) -> int  # 删除的 key 数

# SimpleLongTermMemory
async def soft_delete_session_memories(tenant_id, user_id, session_id) -> int
```

由 `ConversationService._clear_conversation_memories` 调用，**不**在 Repository。

### 画像 adapter

```python
async def load_user_profile(user_id: int, redis_client=None) -> UserProfileData
async def save_user_profile(user_id: int, profile: UserProfileData, redis_client=None) -> bool
```

## B2. 优先级 P0–P3（必须能解释冲突）

| 级 | 内容 | 存储 | 冲突时 |
|---|---|---|---|
| P0 | 最近对话 | Redis ZSET | **最高**，刚说的为准 |
| P1 | 用户画像 | MySQL+缓存 | 次之，可能过时 |
| P2 | 会话摘要 | Redis string | 有损压缩 |
| P3 | 长期语义 | Milvus | 最低，噪声风险 |

文案写在 `memory_context._MEMORY_SECTION_TITLES` + `_MEMORY_INSTRUCTIONS`。

## B6. 降级矩阵（背）

| 故障 | 读 | 写 |
|---|---|---|
| Redis | 空 STM | 跳过 append（warn_once） |
| 画像服务 | {} | debug 日志 |
| Milvus | [] | 跳过 extract 写 / hit |
| before 整体异常 | memory_state=None，主对话继续 | — |
| after 异常 | — | warning，**用户已收到答案不 500** |

## B7. 删会话 vs 跨会话

- 删会话：STM 全清；LTM **仅**带该 `session_id` 的软删  
- 历史无 session_id 的 LTM：**不删**（防误伤跨会话）  
- 画像：durable，**删会话不删画像**  

## B8. 高频追问

1. **为何压缩点才抽 LTM？** 成本 + 语义完整 + 少寒暄污染。  
2. **去重 0.88 vs 检索 0.72？** 写严读松。  
3. **P0 与 P1 冲突？** 跟最近对话。  
4. **MsgPack 为何还要 Zstd？** 长消息省 Redis 内存。  
5. **lock 干嘛？** 压缩并发互斥。  
6. **tenant 现状？** 预留，默认 default。  
7. **profile 在哪个域？** user 拥有；knowledge 只 adapter。  
8. **after 写失败用户感知？** 答案已出，最多丢记忆。  
9. **session_id 从哪来？** configurable.thread_id。  
10. **clear_session 返回值？** 删除 key 数量（int）。

## B9. 口述演示

「每轮问答前 before_agent 拼四层记忆，P0 优先。答完 after_agent 写两条消息；够轮次就压缩，压缩成功才 extract 进 Milvus 并可能更新画像。删会话时库表和 STM/LTM 一起清，但画像保留。」

## 附录 M · 函数手册：记忆系统逐函数明细

> 签名与源码逐字一致（v3.35.1）。📌=每轮对话热路径 🔒=并发语义 ⚠️=历史踩坑。
> 概念叙事见正文 §1–§10；本附录供对照源码逐函数精读。

### M.1 `orchestration/memory_middleware.py`

#### `class MemoryMiddleware.__init__(self, redis_stm, milvus_ltm, memory_extractor, profile_reader=load_user_profile, profile_writer=save_user_profile)`

五依赖全可注入（测试全替身）；读取 `ltm.enabled` 快照；
`_errors_warned: set[str]` 支撑按类去重告警。

#### `def _degrade_once(self, key, operation, exc, **context) -> None`

同类降级只记一次（首个已带堆栈足够定位，不让同一问题每轮刷屏）；
实际分级交给 `log_degradation`（外部故障 warning / 疑似缺陷 exception）。
⚠️ 前身 `_warn_once` 只打固定文案无异常对象——缺陷和抖动在日志里长一样。

#### 📌 `async def before_agent(self, tenant_id, user_id, session_id, user_input) -> AgentMemoryState`

**读扩散入口**（正文 §2.5.3）。三路 `asyncio.gather` 并发：

| 私有方法 | 读什么 | 失败降级 |
|---|---|---|
| `_read_short_term(t,u,s) -> (summary\|None, messages)` | STM 摘要+最近消息（内部再 gather 两条） | `(None, [])` |
| `_read_user_profile(user_id) -> profile \| None` | uid 可转正整数才读；匿名返回 None（不覆盖默认画像） | `{}` |
| `_read_long_term(t,u,input) -> list[MemorySearchResult]` | ltm.enabled 才做 hybrid_search | `[]` |

任一路失败只降级该路；聚合成 `AgentMemoryState` 返回。
并发副作用：三路告警到达顺序不定（测试只断言集合）。

#### 📌 `async def after_agent(self, tenant_id, user_id, session_id, user_message, assistant_message, long_term_memories=None) -> None`

**写扩散执行体**（由 turn_completed 消费者调用；正文 §2.5.2）。三段各自容错：

```text
① STM 落盘：get_meta → total_turns+1 → append_messages(两条一次往返)
   → save_meta → refresh_ttl
② 压缩+抽取：复用①的 meta（⚠️ 曾重复 get_meta 一次）→ should_compress?
   → compress_session_memory(summary_compressor 闭包：build_compression_prompt
   → extractor.llm ainvoke) → 压缩成功且 ltm_enabled →
   extractor.extract → 逐条 deduplicate_memory → save_memory(带 session_id)
   → profile 非空 → profile_writer
③ 命中统计：update_memory_hit_infos(全部命中一次批量 upsert
   ⚠️ 曾逐条往返)
```

WHY 压缩点才抽取：控 LLM 成本 + 积累数轮后语义更完整。

#### `def _parse_numeric_user_id(user_id: str) -> int`

纯函数：可转正整数返回之，否则 0（匿名）。

### M.2 `stm/redis_short_term_memory.py`

#### ⚠️ `def create_stm_redis_client(redis_url: str) -> redis.Redis`

**必须 decode_responses=False**：STM 消息是二进制 MsgPack/Zstd（首字节
\x00–\x03），非法 UTF-8。带解码的客户端写入正常，**zrevrange 读取时
UnicodeDecodeError** 被降级吞掉 → "写得进读不出、最近消息恒为空"
（v3.34 修复的静默故障）。读路径 decode_model/decode_messages 原生支持
bytes；画像缓存 JSON 文本 json.loads 同样接受 bytes。

#### 纯函数层

| 函数 | 签名 | 要点 |
|---|---|---|
| `build_session_keys` | `(key_prefix,t,u,s) -> SessionKeys` | 一次拼 messages/summary/meta/lock 四个 key |
| `decode_model` | `(raw: bytes\|str\|None, model_cls) -> Model\|None` | bytes→utf-8→json→pydantic；非 dict 返回 None |
| `message_score` | `(message) -> int` | created_at 毫秒；秒级历史值（<1e12）回退当前毫秒 |
| `extract_summary_from_response` | `(response) -> SessionSummary\|None` | extract_first_json_object 抠 JSON → 模型化 |
| `decode_messages` | `(raw: list[bytes\|str]) -> list[MessageRecord]` | 逐条 decompress，坏条目 debug 跳过；结果 reverse 成时间正序（zrevrange 是倒序） |
| `split_messages_for_compression` | `(messages, keep_recent_rounds) -> (压缩段, 保留段)` | 一轮≈2 条估算：保留 `rounds*2` 条 |
| `build_runtime_settings` | `(*, config, redis_config, window_config, compression_config) -> ShortTermMemoryRuntimeSettings` | 四个配置节收口成一个 frozen 运行时对象；⚠️ 参数名统一 `runtime`，曾用 `settings` 遮蔽全局同名 |

| `build_compression_context` | `(*, runtime, keys, meta, message_count, old_summary, all_messages) -> CompressionContext\|None` | 未达阈值 None；否则切分消息并快照 old_summary JSON |

#### Redis 往返合并层（⚠️ v3.33 前 4N 次往返）

| 函数 | 行为 |
|---|---|
| `queue_window_pruning(pipe, key, runtime)` | 三条修剪命令入 pipeline：zremrangebyrank(超 16 条)、zremrangebyscore(超 24h)、expire |
| `prune_message_window(*, redis_client, key, runtime)` | 独立修剪入口：pipeline 一次往返 |
